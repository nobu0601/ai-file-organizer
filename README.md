# AI File Organizer（AI 自律型 Windows ファイル整理アプリ）

ダウンロードフォルダや作業フォルダのファイルを、**ファイル名と内容**から理解して整理する Windows 用デスクトップアプリです。
拡張子ではなく「テーマ・プロジェクト・用途」でまとめます。分類体系（どんなフォルダを作るか）は開発者が決めるのではなく、AI が手元のファイル群を分析して考案し、**ユーザーが承認したものだけ**を使います。

- ローカルで完結します。クラウドへファイル内容を送ることはありません（有料 API も不要）
- ローカル LLM（Ollama）があれば使い、無くても内容ベースの分類で全機能が動きます
- 初期状態は**安全なプレビューモード**です。勝手にファイルを動かしません

> **検証状況**: 開発とテストは Linux 上で行いました（pytest 76 件成功、GUI は仮想ディスプレイで起動・操作を確認）。
> **Windows 実機での起動確認はまだ行っていません。** Windows 固有の処理（ジャンクション検出、`os.startfile`、
> スタートアップ登録、`%LOCALAPPDATA%` の解決、`.bat` スクリプト）はコード上で対応していますが、実機では未確認です。

## 2. セットアップ

### かんたんな方法

1. このフォルダを任意の場所に置く（例: `C:\Tools\ai-file-organizer`）
2. `scripts\setup.bat` をダブルクリック
   - プロジェクト内に `.venv`（仮想環境）を作り、そこにだけ依存ライブラリを入れます
   - 既存の Python 環境・PATH・レジストリは変更しません
3. `scripts\run.bat` をダブルクリックで起動

### 手動で行う場合

```bat
cd C:\Tools\ai-file-organizer
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe src\main.py
```

エラーを確認したいときは `scripts\run.bat --console` で起動するとコンソールに表示されます。

### Python が無い場合

python.org から Python 3.12 などをインストールしてください。インストーラーで
「Add python.exe to PATH」と「tcl/tk and IDLE」にチェックを入れます。Microsoft Store 版でも動きますが、python.org 版を推奨します。

### ローカル AI（任意）

1. https://ollama.com から Ollama for Windows をインストール（ARM 版 Surface にも対応しています）
2. アプリの「設定」タブで「推奨モデル ○○ をダウンロード」を押す（コマンド操作は不要）
3. 「Ollama を使う」をオンにして「設定を保存」。モデル欄は `auto` のままで構いません

「推奨モデルをダウンロード」では、次の 2 つを取得します。

- **埋め込みモデル `bge-m3`（約 1.2GB）**: 文書の意味を数値にして、意味の近さでまとめ・分類します。1 ファイル 1 秒未満と速く、分類の中心になります
- **対話型の LLM（下表）**: カテゴリの名前と説明を考え、埋め込みだけでは決めきれないファイルを候補の中から選びます。埋め込みモデルが無い場合は分類全体に使います

モデル欄が `auto` のとき、アプリは PC のメモリを調べ、インストール済みのモデルから動かせる中で最も性能の良いものを自動で使います。
GPU のないノート PC（Surface など）を前提に、CPU で実用的な速さで動く 8B までを候補にしています。
承認・移動したファイルは、カテゴリの特徴として覚えます（使うほど分類が当たりやすくなります。取り消したファイルは外します）。

| メモリ | 推奨モデル | ダウンロード |
|---|---|---|
| 16GB 以上 | `qwen3:8b`（次点 `qwen2.5:7b`） | 約 5GB |
| 8GB | `qwen3:4b`（次点 `qwen2.5:3b`） | 約 2.6GB |
| 4GB | `qwen2.5:1.5b` | 約 1GB |

> qwen3:8b と qwen3:4b の実測結果は「分類精度」の節を参照してください。qwen2.5 系と qwen2.5:1.5b は実測していません。

接続先は `127.0.0.1` / `localhost` のみ許可しています（外部サーバーには接続しません）。
Ollama が止まっていても自動的に内容ベース分類に切り替わります。

## 3. 使い方

起動すると**ホーム**画面が開きます。4 つの手順が上から並び、今やる手順は青い枠と「◀ 次はここ」で示されます。青いボタンを順に押していけば整理できます。

1. **整理するフォルダを選ぶ** — 「フォルダを選ぶ…」で、例えばダウンロードフォルダを選びます
2. **フォルダ分けを決める** — 「AI に提案してもらう」を押すと、AI がファイルの中身を読んでフォルダ分けを提案します。
   「提案を見る」で内容を確認し、よければ「すべて採用」を押します。採用すると整理先にフォルダが作られ、
   提案に含まれていたファイルが「移動待ち」になります（採用するまで、フォルダもファイルも変わりません。ファイルは手順 3 で移動するまで動きません）
3. **確認して移動する** — 移動先の一覧を確認し、「移動待ちをすべて移動」を押します。
   「確認が必要」のファイルは、行を選ぶと移動先の候補が下に入るので、よければ「選んだ移動先へ移動」を押します
4. **これから届くファイルを自動で整理する** — 「見張りを始める」を押すと、新しく届いたファイルを自動で仕分けます。
   初期設定では仕分けだけ行い、移動はあなたの確認後にします

移動は「履歴・元に戻す」画面からいつでも元に戻せます。

デモ用ファイルで試す場合:

```bat
.venv\Scripts\python.exe scripts\create_demo_files.py %USERPROFILE%\Desktop\demo-downloads
```

作成したフォルダを監視対象に登録して試してください（実際のダウンロードフォルダを使わずに動作を確認できます）。

## 5. 仕組み

```
監視（watchdog） → キュー（重複イベント集約・書き込み完了確認・使用中の再試行）
  → 安全チェック（除外・リンク・管理領域・機密・開発プロジェクト）
  → 内容解析（形式別パーサー、サイズ上限あり）
  → 分類（Ollama または内容ベース） → 検証（承認済みか・信頼度・条件一致・命令文混入）
  → 「自動移動」「実行待ち」「要確認」のいずれか → 移動（上書きなし）＋履歴
```

### 分類体系の考案

- ファイル名・元フォルダ名・本文から特徴語を抜き出し（日本語・英語）、TF-IDF の類似度でファイルをまとめます
- まとまりの特徴語からカテゴリ名・説明・分類条件（キーワードと重み）を作ります
- 大きなまとまりの中に明確な小グループがあれば下位カテゴリにします（階層数は固定しません）
- 既存カテゴリに当てはまるファイルは既存カテゴリを再利用し、新しいカテゴリを乱立させません
- 共通点の少ないファイルは無理にカテゴリを作らず「どのカテゴリにも入らない」として残します
- Ollama が使える場合は、カテゴリ名と説明を LLM が考えます（まとめ方自体は内容ベースで決め、結果を安定させます）
- 拡張子は分類の手掛かりに使いません

### 新しいファイルの分類

1. 既存の承認済みカテゴリに当てはまるかを判定
2. 当てはまらない場合だけ新規カテゴリを「提案」（承認されるまで正式体系には反映しない）
3. 統合・分割・階層変更は「統合・分割の変更案を作成」で理由付きの提案を作り、承認を求めます

### 自動移動の条件（すべて満たす場合のみ）

- 自動移動がオン、かつプレビューモードがオフ
- 監視で検出した新規ファイル（または停止中に追加されたファイル）であること。既存ファイルの初回整理はプレビュー経由
- 分類先が存在し、承認済みであること
- 信頼度が閾値（初期 0.85）以上。信頼度は AI の自己申告をそのまま使わず、分類条件との一致度と組み合わせて計算
- カテゴリの分類条件のキーワードと 2 語以上一致
- 内容を正常に読めた（暗号化・パスワード保護・読み取り不能・未対応形式は要確認）
- 機密情報の可能性がない（ファイル名・本文の語で判定）
- Git リポジトリなど開発プロジェクトの内部ではない
- （LLM 使用時）本文に命令文のような記述がない

## 6. 安全対策

- **上書きしない**: Windows では既存ファイルがあると失敗する `os.rename` を使用。同名ファイルがあれば `名前 (1).拡張子` のように別名にします
- 移動前にパス・サイズ・更新日時・SHA-256 を記録し、分類後に変更されたファイルは移動しません
- 移動先は整理先フォルダの内側に限定し、`..`・予約名（CON など）・禁止文字・リンクを含むパスを拒否します
- AI が出したカテゴリ名やパスはそのまま使わず、承認状態・存在・パスの安全性を検証します
- シンボリックリンク・ジャンクションは辿りません
- 整理先フォルダとアプリのデータ領域は監視・処理の対象外です（再分類のループを防止）
- 取り消したファイルは再処理しません
- 初期設定で移動禁止: `.git` `.venv` `venv` `node_modules` `__pycache__` などのフォルダ、`.env`・秘密鍵（`id_rsa` `*.pem` `*.key` など）・認証情報らしき名前、ロックファイル、仮想マシンイメージ、データベース、実行ファイル、ダウンロード途中の一時ファイル
- ソースコードは内容を読むだけで、**実行しません**。文書内の命令文にも従いません（LLM にはデータとして渡します）
- 大きなファイルは先頭の設定サイズ（初期 4MB）までしか読みません
- エラーが起きたファイルは「失敗」として記録し、他のファイルの処理は続けます

### 取り消しの条件

- 移動先にファイルが存在する
- 元の場所に別のファイルがない（ある場合は上書きせず、理由を表示）
- 移動後に内容が変更されていない（SHA-256 とサイズで確認）

## 7. データの保存場所

`%LOCALAPPDATA%\AIFileOrganizer\`

| パス | 内容 |
|---|---|
| `settings.json` | 設定（見本: `config/settings.example.json`） |
| `history.sqlite3` | 操作履歴・ファイルの処理状態・AI の提案 |
| `logs\app.log` | ログ（2MB × 5 世代でローテーション） |
| `taxonomy\folder_map.json` | 承認済みの分類体系（機械処理用。JSON Schema で検証） |
| `taxonomy\folder_map.md` | 分類体系の説明書（人間向け） |
| `taxonomy\folder_map_history\` | 分類体系の変更履歴（変更前後のバージョン・日時・理由・操作・前後のスナップショット） |

整理されたファイルは、設定の「整理先フォルダ」（初期値 `ドキュメント\AI整理フォルダ`）の下にカテゴリ名のフォルダで置かれます。
カテゴリには `cat-xxxxxxxxxxxx` 形式の固定 ID が付き、名前を変えても ID は変わりません。
名前を変えた場合、実フォルダは自動では改名しません。「整合性チェック」で改名案が表示され、適用するかを選べます。
整合性チェックは、不一致を見つけてもフォルダを削除・改名せず、修正案だけを表示します（自動で適用できるのは作成と、改名先が空いている場合の改名のみ）。

### 分類精度

正解ラベル付きの架空ファイルで測定しています（`scripts/eval/`）。

- A（8 テーマ・80 件）: 調整に使ったデータ
- B（7 テーマ・70 件）: 調整に使っていないデータ
- C（10 テーマ・132 件）: 調整に使っていないデータ。ただし、誤った自動移動の原因調査に使いました（安全条件の考え方を見直すためで、数値は合わせていません）

GPU なし・CPU 4 コア・メモリ 16GB の環境で、Ollama 0.40.9 を使って測りました（2026 年 10 月）。

| 新規ファイルの正解率 | 内容ベース（LLM なし） | qwen3:8b のみ | 埋め込み bge-m3 のみ | **埋め込み + qwen3:8b** |
|---|---|---|---|---|
| A | 53% | 84%※ | 91% | **100%** |
| B | 36% | 68%※ | 64% | **75%** |
| C | 45% | 63% | 65% | **80%** |
| C のうち名前に手掛かりのないファイル | 38% | 62% | 38% | **76%** |
| 自動移動（正しい／件数、C） | 7/7 | 12/12 | 7/7 | 7/7 |
| 誤った自動移動・無関係ファイルの移動 | 0 件 | 0 件（C で確認）※ | 0 件 | 0 件 |
| 1 ファイルあたりの処理時間（目安） | 0.1 秒未満 | 約 20〜26 秒 | 約 0.4 秒 | 約 10〜15 秒（迷ったファイルだけ LLM を使用） |

※ qwen3:8b のみの A・B は、汎用語の除外と一致条件の強化（下記）を入れる前のコードでの測定値です。

**自信のない候補の表示**: 確からしさの低い候補（50% 未満）は、「確認して移動」画面で「（自信なし）」付きの薄い文字で表示します。
「自信のない候補も表示する」のチェックを外すと隠せます。無関係なファイルに付く見当違いの候補は、多くがこの自信のない候補です。

**埋め込み + LLM の組み合わせ**: 埋め込みで候補を上位 4 件に絞り、埋め込みだけでは決めきれない（信頼度 0.85 未満の）ファイルについてだけ、
LLM に候補の中から選ばせます（各候補に代表ファイル名を添えます）。埋め込みが確信しているファイルは LLM を使わないため速く処理されます。
LLM が埋め込みの 1 位と違う候補を選んだ場合や「該当なし」と答えた場合は、自動移動せず候補付きの要確認にします。
Ollama で埋め込みモデルと LLM の両方がインストールされていれば、この方式が自動で使われます。

- 正解率は、承認後に追加したファイルに正しいカテゴリが表示された割合です（自動移動されず、要確認の候補として表示された場合を含む）
- 自動移動は、信頼度が 0.85 以上で、しかも内容ベース分類が同じカテゴリを 1 位に選び、自身の信頼度も 0.6 以上の場合だけ行います。どちらかの判断が割れたファイルは、候補付きの要確認になります
- 「記録」「時間」「日付」「比較」のような、表やメモに共通する語は手掛かりにしません（評価データ C で、これらの語のカテゴリへ無関係なファイルが自動移動されたため）
- 意味の近さが弱いもの（類似度 0.60 未満）は候補を出しません
- 再測定: `python scripts/eval_accuracy.py --dataset scripts/eval/dataset_c.json --embed bge-m3 --models qwen3:8b`

### 既知の制限

- 内容ベース分類は語の一致に基づくため、語彙が極端に少ないファイル（本文がほぼ無い画像など）はカテゴリに入りにくく、要確認になりやすいです
- 画像はファイル名とサイズ・縦横のメタデータのみ使います（ローカル画像認識は `ImageRecognizer` を実装すれば追加できる設計です）
- 旧形式の Office ファイル（.doc / .xls / .ppt）は本文を解析せず、要確認になります
- 「停止中に追加されたファイル」は更新日時で判定します。古い更新日時のままコピーされたファイルは、安全側（プレビュー扱い）に倒れます
